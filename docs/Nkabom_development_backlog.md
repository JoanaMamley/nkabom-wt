# Nkabom: development backlog (Release 1)

Nkabom: the WomenTrust alumnae community. Backlog for developers, 17 October 2026.

82 stories in seven epics, ordered so each epic builds on the one before it. Points are a rough size (1 = a few hours, 3 = about a day, 5 = two to three days, 8 = a week). Each story names the requirements it covers (FR numbers from the requirements doc) and ends with its "done when" check. Stack: Angular, Firebase on the free Spark plan (Hosting, Authentication, Firestore, Cloud Messaging), a Cloudflare Worker for server code (the app's API, scheduled jobs and queues), and Workers KV for photos and backups. Everything runs on free plans, with no card on Google or Cloudflare (requirements, Technology stack). Stories written before the move to Workers say Cloud Functions; NKB-114 to NKB-120 move that code to the Worker. The developer makes every decision, including the open ones listed at the end of the requirements doc.

## 1. Foundation and infrastructure

- **NKB-101 · Initialise repositories and local environment** (2 pts) · FR-8.7 Angular app and a Firebase project (Hosting, Authentication, Firestore, Functions), with the Firebase Emulator Suite for local work. *Done when:* one command starts everything locally, lint and formatting run, and no secrets are committed.

- **NKB-103 · Firestore data model** (5 pts) · FR-1.5, FR-2.6 User with role (member, admin, primary admin) and member profile with status (pending, active, rejected, deactivated). *Done when:* the collections can be created from scratch in the emulator and one profile per user is enforced by using the user ID as the document ID.
- **NKB-104 · Audit log service** (3 pts) · FR-8.3 A reusable function that records actor, action, target, and time. *Done when:* entries cannot be edited or deleted from the app and later stories can call it with one line. Moved to the Worker in NKB-117.
- **NKB-105 · Photo storage on Cloudflare R2** (3 pts) · FR-2.3, FR-8.2 Private Cloudflare R2 bucket, with a Cloud Function issuing short-lived signed URLs for upload and download. Checking against a real bucket needs the Cloudflare account from NKB-113. *Done when:* an uploaded file cannot be opened without a valid signed link. Superseded: R2 needs a payment method on file, so NKB-115 moves photos to Workers KV, with links signed by the Worker.
- **NKB-106 · Email service and templates** (3 pts) · FR-8.5 One send function over a free-tier transactional email provider, called from Cloud Functions, with templates kept in one place. *Done when:* the provider can be swapped by configuration and failed sends are logged. Moved to the Worker in NKB-116, which sends through the shared Gmail account instead of Brevo.
- **NKB-107 · PWA shell** (3 pts) · FR-4.10 Angular PWA setup with manifest, icons, service worker, and an offline fallback page, served over HTTPS from Firebase Hosting. *Done when:* the app can be installed on Android and iPhone and passes the Lighthouse installability check.
- **NKB-108 · Light and dark theme** (3 pts) · FR-8.8, FR-8.9, FR-8.10 Toggle on every page, default from the device setting, choice remembered. *Done when:* every screen is readable in both modes and the choice survives a reload.
- **NKB-109 · Firebase environments and backups** (3 pts) · FR-8.2, FR-8.6 Separate staging and production Firebase projects, scheduled Firestore exports for backups, HTTPS, and secrets kept in Functions configuration. Both projects sit under the shared project Google account; creating them is done in NKB-113, the first staging deploy in NKB-114 and the restore test in NKB-119. Automated deploys come in NKB-121. *Done when:* the backup function, staging and production config, and deploy scripts are in place and tested, and the project set-up and restore steps are written up in the README. Scheduled Firestore exports need the paid Blaze plan, so backups move to Workers KV in NKB-119 and the Functions configuration to the Worker in NKB-114.
- **NKB-110 · Scheduled Cloud Functions** (3 pts) Scheduled functions with retries for the reminder and sync jobs. Checking the sample job on staging is done in NKB-113. *Done when:* a sample scheduled job is in place, tests show it retries on failure and logs errors, and the staging check is written up in the README. Cloud Scheduler needs Blaze, so scheduled jobs move to Worker Cron Triggers and Queues in NKB-118.

* **NKB-111 · Admin-only and member-visible data split** (5 pts) · FR-3.1, FR-5.2 Full member records, including date of birth, in an admin-only collection, and a limited directory record (name, photo, occupation or course, graduation year) in a collection members can read, kept in sync by a function. *Done when:* emulator tests show a member can read the directory but never the full record. The sync moves from a Firestore trigger into the Worker in NKB-117.
* **NKB-112 · Cost guardrails** (2 pts) Blaze plan with a budget alert well under the $5-a-month limit ($1.50 for production, $0.50 for staging), a cap that turns off a project's billing when its budget is reached, a limit on function instances, usage checks for Firestore, Functions, and R2, and a handbook note on what to do if the alert fires. Setting up the budgets and testing the alert are done in NKB-113. *Done when:* the cap function, instance limit, and budget script are in place and tested, and the handbook note covers the monthly checks, what to do at each alert, and how to test the alert and the cap. Superseded: the projects stay on the free Spark plan, which cannot be billed, so NKB-120 removes the budget, the cap and the instance limit; the monthly usage checks stay.
* **NKB-113 · Shared project accounts** (3 pts) · FR-8.7 A shared Google account for the project, created by the developer, that owns the Firebase projects (NKB-109) and the calendar service account (NKB-501), plus the Cloudflare account for Workers and Workers KV (NKB-114) and its Gmail account sends the app's email (NKB-116). Turn on 2-step verification, keep backup codes and a recovery email and phone outside the account. No card goes on Google or Cloudflare: both Firebase projects stay on the free Spark plan, and Cloudflare is used only on the Workers free plan, with Workers KV for photos and backups. Following `docs/handbook/account-setup.md` and the README: create `nkabom-staging` and `nkabom-prod` on Spark, each with a Firestore database in the same location; copy each project's web config into `environment.staging.ts` and `environment.ts` locally, and keep it out of the repo with `git update-index --skip-worktree`. The checks on staging move to the stories that make them possible: the first deploy to NKB-114, the scheduled triggers to NKB-118, and the restore test to NKB-119. *Done when:* the Google and Cloudflare accounts exist, signing in does not depend on a single phone, the access and recovery details are kept in a private record outside the repo, which the handbook (NKB-708) points to, and both Firebase projects exist on Spark with a Firestore database and a registered web app.
* **NKB-114 · Worker foundation** (5 pts) · FR-1.11, FR-8.2 A `worker/` project for one Cloudflare Worker per environment (`nkabom-api-staging`, `nkabom-api-prod`) on the free plan, at its `workers.dev` address. It is the app's API: each endpoint checks the caller's Firebase ID token, then acts on Firestore and Firebase Auth through their REST APIs with a service account key held as a Worker secret, alongside the Gmail sending credentials and the key that signs photo links. Each environment has its own Workers KV namespaces for photos and backups. Writes with side effects (registration, profile edits, approvals, admin changes, mentorship, publishing, exports) go through it; the app reads Firestore directly. Includes CORS, local development with `wrangler dev` against the Firebase emulators, Vitest with the Workers pool, a CI job, and deploy scripts. Also does the first deploy to staging, following the README: create the service account key, set the Worker secrets and the KV namespaces for both environments, and deploy Hosting, Firestore rules and the Worker with `npm run deploy:staging` (from NKB-113). *Done when:* a test endpoint rejects a missing or forged token and reads Firestore with a valid one, locally and on staging, a manual deploy to staging works, and CI runs the Worker's lint, tests and build.
* **NKB-115 · Photos in Workers KV** (3 pts) · FR-2.3, FR-8.2 Replace the R2 bucket (NKB-105), which needs a payment method on file, with a private Workers KV namespace per environment, read and written only by the Worker. The Worker issues its own short-lived signed links (an HMAC over the path, method and expiry, keyed by a Worker secret): a 5-minute upload link that accepts only the declared type and exact size, and a 10-minute download link, keeping NKB-105's path shape and limits. Photos are about 100 KB after resizing, so 1,000 members fit well within KV's free 1 GB. *Done when:* a photo cannot be uploaded or read without a valid, unexpired link, and NKB-105's type and size checks pass against the Worker.
* **NKB-116 · Email through Gmail on the Worker** (3 pts) · FR-8.5 Move `sendEmail` and the templates (NKB-106) to the Worker, and add a Gmail provider as the default, since Brevo needs a domain the project does not have. It sends through Gmail's mail server (`smtp.gmail.com`) as the shared project account, using an app password (the account has 2-Step Verification) held only as a Worker secret, over the Workers TCP sockets API, building the plain-text and HTML message itself. Check first that a deployed Worker can reach Gmail on port 465 or 587 (Workers block only port 25). Changing the account's password cancels the app password, and the README says how to make a new one. Check Google's current daily sending limit for a free account (sources give 100 to 500 recipients) and set the batch size for large sends (FR-2.5) from it. The Brevo provider stays as an alternative. *Done when:* a test email from staging arrives from the shared Gmail address, failed sends are logged, and NKB-106's tests pass.
* **NKB-117 · Users, directory and audit log on the Worker** (3 pts) · FR-1.5, FR-3.1, FR-5.2, FR-8.3 Create the `users` record on the first Worker call after sign-up instead of an Auth trigger, run the directory sync (NKB-111) in the same transaction as each profile or status change, and move `recordAudit` (NKB-104). Registration submits and profile edits move from direct writes to Worker endpoints, and the rules deny those client writes. *Done when:* the NKB-111 checks pass, the rules tests show members can no longer write profiles directly, and a new account gets its `users` record on its first call.
* **NKB-118 · Scheduled jobs and queues** (3 pts) Two Cron Triggers per environment (daily, and every 5 minutes), within the free plan's 5 per account, and a Cloudflare Queue for bulk and retried work, with automatic retries and backoff. Each run is logged with its job name and outcome, and its last status is kept in Firestore, since Worker logs last only 3 days. Repeated failures email a Primary Admin. Replaces the NKB-110 helper and heartbeat. *Done when:* tests show a failed task is retried and logged, a sample task runs from each trigger locally, and on staging (following the README) both triggers have run, a forced failure was retried and logged, and the sample task is then removed.
* **NKB-119 · Backups to Workers KV** (5 pts) · FR-8.6 A daily task exports every Firestore collection through the REST API, in queued batches within the free plan's limits, as JSON to a private Workers KV namespace per environment, each value under KV's 25 MB limit and set to expire after 30 days. The audit log is exported incrementally, since it only grows. Writes stay well within KV's free 1,000 a day. A restore script reads a backup through Cloudflare's API and loads it into the emulator to check it, then into a project. *Done when:* an export restores into the emulator with the same documents, the backup and restore steps are written up in the README, and a backup taken on staging has been restored once into the emulator and recorded in the README.
* **NKB-120 · Remove the Blaze set-up** (2 pts) Delete Cloud Functions (`functions/`), the budget cap, instance limit and budget script (NKB-112), the Cloud Storage backup set-up (NKB-109), the R2 set-up and AWS SDK (NKB-105) and the heartbeat (NKB-110), and update `firebase.json`, the scripts, CI, the README and `docs/handbook/costs.md`. *Done when:* nothing in the repo deploys Cloud Functions or needs the Blaze plan, and the docs describe only the Spark and Workers set-up.
* **NKB-121 · Continuous deployment** (3 pts) · FR-8.2 GitHub Actions deploys Hosting, Firestore rules and indexes, and the Worker together: to staging on every merge to main, and to production on a tagged release that needs manual approval in a GitHub environment. It signs in to Firebase with Workload Identity Federation, so no service account key is stored in GitHub, and to Cloudflare with an API token kept in GitHub secrets. Deploys run only after the CI check passes. Each pull request gets a Hosting preview channel against staging. The Firebase web config is not committed, so the workflow writes `environment.ts` and `environment.staging.ts` from GitHub secrets before building, and CI builds with stand-in values. Depends on NKB-109, NKB-114 and NKB-120, so there is one clean set-up to deploy. *Done when:* a merge to main reaches staging without manual steps, production changes only after approval, and a failed CI check blocks the deploy.
